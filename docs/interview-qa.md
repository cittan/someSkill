# 模块二：Excel 批量导入

## Q2.1 为什么用 EasyExcel，不用原生 POI？

- **第一层**：EasyExcel 读大文件不撑爆内存，POI 会。
- **第二层（原因）**：xlsx 文件本质是个压缩包，里面装着 XML。POI 的做法是把整个文件全解析成 Java 对象放进内存——一个单元格的对象比它装的数据还大好几倍，几万行就内存溢出（OOM）了。EasyExcel 逐行读：读到一行就回调一次 `invoke()` 方法告诉你"这行来了"，你处理完这行，它就扔掉继续读下一行。内存里永远只有当前一行。
- **第三层（追问"写入呢"）**：导出大文件也一样省内存，但如果数据源本身就在内存里，优势打折。导出的正确做法是分页查询 + 流式写 + 限制导出量。

代码位置：监听器回调 `ExcelImportService.java L97`（`invoke` 方法）。

## Q2.2 一条数据都没进数据库前，发生了什么？（流程题）

按顺序背：

1. 前端把文件装进 FormData（一种能同时装文件和文字的"快递箱"），请求类型是 multipart/form-data；
2. 后端 Tomcat 收到后把文件写到磁盘临时文件（超过 10KB 就落盘，不占内存），配置了 20MB 上限防恶意大文件；
3. 登录拦截器验证 token，把当前用户放进 ThreadLocal；
4. Controller 检查是不是 HR（不是就 403）；
5. Service 里 EasyExcel 逐行读，每攒满 500 行：校验 → 转换 → 事务入库 → 清空缓冲区继续。

**注意一个常见口误**：不是"读完所有行再处理"，是**攒一批处理一批**。这两句话在面试里说混了，面试官会立刻追问内存模型。

代码位置：攒批逻辑 `ExcelImportService.java L103`（`buffer.size() == BATCH_SIZE` 时调 `processBatch`）。

## Q2.3 为什么敢"部分导入"？一条错全回滚不行吗？

- **第一层**：业务场景决定的。迁移的旧数据本来就脏，全量回滚意味着甲方要反复修数据、反复重传。部分导入让干净数据先进库，坏行出报告，修完补传。
- **第二层（实现）**：校验失败的行只是记进报告（行号+原因），**不抛异常不中断**；每 500 行一批，每批一个独立事务——批内要么全进要么全不进，批与批互不影响。
- **第三层（宕机怎么办）**：已提交的批次不回滚（这就是牺牲原子性的代价）；但整个导入**按工号幂等**——同一个文件重传，已入库的工号会被"工号已存在"校验拦下，只补进没导进去的行。
- **收尾加分**："如果是金融对账这种必须全对全错的场景，我会改回一个大事务——这是业务属性决定的取舍，不是技术偏好。"

代码位置：错误收集 `ExcelImportService.java L173`（catch 后只记报告）；批量入库 `ExcelImportService.java L180`（`transactionTemplate` 包裹 `insertBatch`）。

## Q2.4 "幂等"到底是什么？怎么实现的？

**幂等 = 同一个操作做一次和做 N 次，结果一样。** 对导入来说就是：文件重传多少次，都不会插入重复数据。

实现分两个位置配合：

1. **批量预查**（处理每批之前）：拿这批的 500 个工号去库里查一次 `WHERE emp_no IN (...)`，捞出一个 Set；
2. **逐行比对**（循环里）：`dbEmpNos.contains(工号)` 是内存比对，纳秒级。命中就抛"工号已存在于系统"，这行进错误报告，不插入。

代码位置：`ExcelImportService.java L214`（库内工号拦截）。

**重跑场景完整走一遍**：第一次导到第 40 批宕机 → 前 39 批已在库 → 重传同一文件 → 每批预查都发现工号已存在 → 全部拦下 → 只补剩余的行。

**诚实交代缺陷**："先查后插"有时间差（查的时候没有，插之前别人插了），并发上传相同工号时靠数据库唯一索引兜底——当前代码没 catch 约束冲突异常，这是已知待完善点。

## Q2.5 工号没规律，怎么收集去比对？（防口误）

**不需要规律。** 预查的工号不是"推算"出来的，是从 Excel 行对象里**原样抄**出来的（每行的工号字段是什么就收集什么）。IN 查询是精确匹配，走 emp_no 唯一索引，值长什么样不影响。

真正的问题是大 IN 的参数量：5 万个工号一次 IN 有点大。解决梯度：分片查（每 1000 个一查）→ 当前攒批模式下天然每批只查 500 个 → 几十万级改临时表 JOIN。

## Q2.6 没有唯一键的数据怎么保证幂等？

按优先级三招：

1. **拼组合键**：比如"姓名+手机号+入职日期"拼起来当行身份，建复合唯一索引；
2. **整行内容做哈希指纹**：全字段拼一起算 SHA-256，给指纹列建唯一索引。缺点：改一个字段就算新行，只适合"只增不改"的数据；
3. **暂存表**（数据迁移的正统做法）：Excel 全量先倒进 staging 临时表，再用一条 SQL 在库内去重合并（`INSERT ... SELECT ... WHERE NOT EXISTS` 或 PG 的 `ON CONFLICT DO NOTHING`），顺便消掉了"先查后插"的时间差。

一句话：**幂等的前提是先定义"什么算同一行"。**

## Q2.7 5 万条怎么保证导入性能？

三个设计（每个都能展开讲）：

1. **批量预查，不逐行查库**：部门表一次全捞 + 每批工号一次 IN 查询，之后校验全在内存比对。反面教材：逐行查库 = 每行 2 次 SQL，5 万行 10 万次，光网络往返就上百秒；
2. **批量插入**：MyBatis `foreach` 把 500 行拼成**一条**多值 INSERT（见 Q5.3）；
3. **流式解析**：内存里同时只有一批数据，和总行数无关。

## Q2.8 能扛几十万、上百万吗？（二轮面试原题）

两堵墙，按顺序倒：

- **时间墙（先倒）**：30 万行全程 30-60 秒，同步 HTTP 撑不住——Nginx 默认 60 秒超时返回 504，但后端还在跑；用户看"失败"就再传一次；没有任何进度反馈。
  **解法：异步化**（已实现，见 Q2.13-2.15）。
- **内存墙（已通过攒批重构解决）**：旧版监听器把所有行攒进一个 List 全量收集，流式白流了。重构后边读边处理，内存只和批次大小（500）有关。
  **这个故事本身是加分项**："我发现初版全量收集抵消了流式的收益，重构为攒批即处理，内存从和总行数成正比降到和批次大小成正比。"

更大数量级的配置清单：multipart 上限调大、PG JDBC URL 加 `reWriteBatchedInserts=true`、大批量插入后跑 `ANALYZE`。再大上 PG 的 `COPY` 命令（专门的批量装载通道，比 INSERT 快一个量级）。

## Q2.9 校验了什么？转换了什么？

校验链（按顺序，便宜的在前）：

1. 必填：工号、姓名、部门、手机号
2. 格式：手机号正则、身份证 18 位
3. 部门存在：部门名必须能在部门表对上（否则 dept_id 挂空）
4. 重复：文件内工号重复 + 库内工号重复

代码位置：`ExcelImportService.java L199-L214`。

字段转换（旧系统 → 新系统）：

| 旧系统的值 | 新系统的值 | 为什么转 |
|---|---|---|
| 状态码 "1"/"2"/"3" | ACTIVE / RESIGNED / PROBATION | 数字代码换成有含义的枚举 |
| 部门名"技术部" | dept_id = 1 | 数据库靠 ID 关联，名字会改 ID 不会 |
| "2021/3/15" 等多种格式 | 统一的日期对象 | 旧数据格式五花八门，逐一尝试解析 |

## Q2.10 为什么行模型的字段全是 String？

Excel 里 `13812345678` 会被当成数字，Java 按数值类型读出来变成科学计数法 `1.3812345678E10`——手机号直接报废。所以接收时全用 String 拿原始文本，转换的事留到校验阶段自己做。**这是真实踩坑点，值得主动讲。**

## Q2.11 错误报告长什么样？怎么补数据？

```json
{ "total": 2000, "successCount": 1993, "failedCount": 7,
  "errors": [ { "rowIndex": 37, "reason": "手机号格式非法: 12345" } ] }
```

行号是 Excel 里的直观行号（解析时的 0 起行号 +1），用户拿报告能直接翻到 Excel 第 37 行。补数方式：修完错**整个文件重传**——幂等保证只进新行，不需要做"部分重传"功能。

## Q2.12 流式读取到底解决/没解决什么？（二轮面试踩过的坑）

- **解决了**：解析层的内存——POI 要把整个文件的 DOM 对象全放内存（单元格对象比数据本身大好几倍），EasyExcel 把这部分降到只有一行。
- **没解决（重构前）**：业务层的全量收集——监听器里 `rows.add(row)` 把所有行攒进 List，转换后又一份，流式的收益被吃回去了。好比**水龙头换成了细水长流，但浴缸不排水**。
- **重构后**：攒批即处理，两层都 O(1)（相对批次）。

**这题的教训**：说自己代码时，先分清"当前实现"和"改造方案"——把还没写的方案说成现状，被翻代码就穿帮。

## Q2.13 导入为什么改成了异步？整体怎么跑的？（已实现，必背）

**同步的问题**：大文件导入几十秒起步，HTTP 请求挂着等——网关超时、用户重复点、看不到进度。

**改造后的完整链路**：

```
POST /api/employees/import（HR 上传）
   请求线程只做三件事：校验 HR 权限 → 文件落盘临时文件 → 提交线程池 → 立刻返回 taskId
        ↓
   excel-import-N 后台线程执行导入（攒批处理 + 每批上报进度）
        ↓
GET /api/employees/import/tasks/{taskId}  ← 前端每秒轮询
   返回状态/已处理行数/最终报告，终态停止轮询并刷新列表
```

代码位置：提交入口 `ImportTaskService.java L52`（`submit`）；后台执行 `ImportTaskService.java L88`（`run`）；轮询接口 `EmployeeController.java L60`。

## Q2.14 线程池参数怎么设的？为什么？（IO 密集型，必背）

代码位置：`ImportExecutorConfig.java L39`。手动 `new ThreadPoolExecutor`，不用 Executors 工厂方法。

| 参数 | 值 | 为什么 |
|---|---|---|
| 核心线程数 | CPU 核数 × 2 | 导入是 IO 密集型：线程大部分时间在等文件、等数据库，不是烧 CPU，所以可以多于核数。（CPU 密集型才设 核数+1） |
| 最大线程数 | CPU 核数 × 4 | 高峰期扩容上限 |
| 队列 | **有界**，容量 50 | 防止无界堆积把内存拖垮——`Executors.newFixedThreadPool` 的队列无界，是阿里规约禁用工厂方法的核心原因。10 个 HR 反复传时任务排队执行，排队对用户可接受（有进度条） |
| 拒绝策略 | AbortPolicy | 队列满抛异常，提交方 catch 后返回"队列已满请稍后再试"。**不选 CallerRuns**：它会让 Tomcat 的 Web 线程亲自去跑导入，异步退化回同步，占住 Web 线程一两分钟 |
| 停机 | @PreDestroy：shutdown → 等 30 秒 → shutdownNow | 应用重启时不把在跑的导入腰斩。注意原生 ThreadPoolExecutor 没有那套 setter API，要手动写（`ImportExecutorConfig.java L52`） |

## Q2.15 异步化的三个细节（面试深挖点）

1. **为什么必须在请求线程里把 MultipartFile 落盘？** 上传文件的输入流只在本次请求的生命周期内有效，请求结束就失效了。所以请求线程内先 `transferTo` 写到磁盘临时文件，后台线程读磁盘文件（`ImportTaskService.java L60`）。
2. **为什么权限在提交时校验，不在后台线程校验？** 登录用户存在 ThreadLocal 里，它绑定的是请求线程——后台线程里取不到。而且"提交那一刻有没有权限"才是正确语义。
3. **任务状态存哪？** 内存 ConcurrentHashMap——**演示级简化**，重启就丢。生产方案：任务表或 Redis；多实例部署时轮询请求要能打到任意实例，必须共享存储。**主动说出这个简化是加分项。**

## Q2.16 拿到别人的 token 能干什么？（攻击链题，二轮原题）

场景：攻击者偷了 HR 的 token，用 Postman 直接调导入接口，Excel 里把张三薪资改成 1 块。

**逐道防线走一遍**：

- 登录拦截器：token 是真的，放行——**拦不住**（它验证的是凭证，不是持证人）；
- 功能权限：HR 确实能导入——**拦不住**；
- 工号校验：张三已在库，"工号已存在"把这行拦进错误报告——**"改数据"失败！**

**关键认知**：改薪资失败不是因为系统"识别出恶意修改"，而是**导入接口压根没有 UPDATE 能力**——它的世界里只有"新员工"和"重复员工"，重复的整行丢弃，连薪资字段都没读过。这是 INSERT-only 语义的安全红利。

**但攻击没完全失败**：文件里新造一个工号的伪造员工，会正常入库。堵它靠：审计日志（事后定位"这次导入不是 HR 本人"）、高风险操作二次认证（输密码/短信验证）、token 加过期时间（偷来的 token 寿命有限）。

**答题心法**：安全题先顺着攻击者路径走一遍，看每道防线是拦住还是放行，再针对放行的环节补——不要第一反应"加个中间件"。

## Q2.17 业务涨到 50 万员工、10 个 HR 每天传，先崩什么？（二轮原题）

两个变量制造不同压力：50 万 = 单次导入变慢（撞时间墙）；10 个 HR = 并发任务变多（撞资源和竞态）。

**按优先级三条**：

1. **P0 异步化**（已实现）：同时化解超时和资源挤兑。HTTP 毫秒级返回；线程池固定大小，任务排队不并发挤兑 Tomcat。先保命——系统不被拖垮，别的问题才有得谈。
2. **P1 并发幂等强保证**：异步化后不同任务真的可能同时插相同工号了。补 catch 唯一约束冲突（`DataIntegrityViolationException`），降级为逐行插入，撞的那行计入错误报告。数据库唯一索引从"兜底"升级为"正式防线"。
3. **P2 批量插入升级**：50 万行用 PG 的 `COPY` 命令——先 COPY 进临时表，再 `INSERT ... SELECT ... WHERE NOT EXISTS` 合并，去重顺带下沉到 SQL 层。

**排序逻辑**（比答案本身重要）：**先保命（可用性），再保对（正确性），最后提速（性能）。**

# 模块三：权限与脱敏

## Q3.1 "角色矩阵"到底是什么？别被词唬住

就是一张**写死的对照表（Map 字典）**。每个角色一本字典：

```java
// RoleEnum.java L33 起，每个角色一段
EMPLOYEE(DeptScope.CURRENT_DEPT, Map.of(
        SensitiveLevel.PUBLIC,       Visibility.PLAIN,    // 公开字段 → 明文
        SensitiveLevel.INTERNAL,     Visibility.MASKED,   // 部门内字段 → 打码
        SensitiveLevel.SENSITIVE,    Visibility.MASKED,   // 手机号 → 打码
        SensitiveLevel.CONFIDENTIAL, Visibility.HIDDEN,   // 身份证 → 不返回
        SensitiveLevel.SALARY,       Visibility.HIDDEN))  // 薪资 → 不返回
```

**"矩阵操作"= 三步**：拿角色取出他的字典 → 拿字段级别查字典 → 按查出的结果（明文/打码/不给）执行对应的 if 分支。没有框架没有魔法。

查询入口只有一个方法（`RoleEnum.java L75`）：

```java
public Visibility visibilityOf(SensitiveLevel level) {
    return matrix.getOrDefault(level, Visibility.HIDDEN);  // 查不到默认"不给"
}
```

**默认值是 HIDDEN（默认拒绝）**：新字段忘了配规则 → 按最严处理 → 配错的后果是"看不见"，永远不会是"泄露"。这是安全系统的黄金法则。

## Q3.2 字段和级别的关联在哪"设置"？（连环追问点）

**当前实现是隐式的**：`phone` 属于 SENSITIVE 级别，仅仅因为 `vo.setPhone(...)` 这行代码写在查了 SENSITIVE 的那个 if 块里（`EmployeeService.java L111-L116`）。没有任何一行"配置语句"声明这个归属——**关联 = 代码位置**。

**隐藏的实现不是"查出来再藏"**：是那个 if 分支不执行 → VO 字段从没被赋值 → 保持 null → 序列化时 key 直接消失。敏感数据从实体到 VO 只有 setXxx() 一条路，那条路上的检查站不放行，数据就没有通道。

**两个阶段分清**（口述别混）：

| 环节 | 谁决定 | 何时 |
|---|---|---|
| 字段归哪个级别 | 开发者（代码写在哪个组） | 写代码时，与角色无关 |
| 某次查询明文/打码/隐藏 | 查字典自动完成 | 每次请求，与开发者无关 |

**演进方案（主动讲是加分项）**：VO 字段上加 `@Sensitive(SensitiveLevel.SENSITIVE)` 注解 + 自定义 Jackson 序列化器统一处理，显式声明、未标注默认隐藏、toVO 的 40 行 if 全删。

## Q3.3 为什么不用 RBAC 五张表？

五表（user/role/permission 加两张关联表）适合"权限要运营人员随时配"的场景。本项目角色就 5 种、稳定不变，规则本质是**代码策略不是业务数据**——用枚举：零查库开销、规则集中一目了然、编译期保证结构、单测直接跑。

被问"以后要动态配权怎么办"："把矩阵的数据来源换成 permission 表加缓存，查询入口 `visibilityOf()` 签名不变，调用方一行不用改——当初收敛成单一入口就是为了这一天。"

## Q3.4 过滤和脱敏是一回事吗？（简历两个词，必须分清）

- **过滤（HIDDEN）**：字段整个不返回。JSON 里**连 key 都没有**——不是 `salary: null`，是不存在 salary 这个字段；
- **脱敏（MASKED）**：字段返回但打码，如 `138****5678`；
- 一句话：**过滤防"不该知道的人"**（薪资对非 HR 连打码值都不给看）；**脱敏防"要用但不需要完整值的人"**（考勤员要打电话，但不需要完整身份证）。

实现位置：脱敏/赋值在 `EmployeeService.java L101-L129`（toVO 的三档 if）；key 消失靠 VO 上的 `@JsonInclude(NON_NULL)` 注解。

## Q3.5 为什么脱敏必须在后端？前端打码不行吗？（最危险的一问）

**前端打码 = 数据已经泄露**。明文先完整到达浏览器，页面只是"画的时候遮一下"：

- F12 → Network 面板记录的是**网络层收到的原始响应**，你的 React/Axios 代码跑在它之后——明文都在；
- 用户可以在控制台用 fetch 带 token 直接调接口，**完全绕过你的前端代码**——前端的一切逻辑对用户是"可选项"。

**标准话术**："前端权限控制只决定'渲染什么'，永远不能决定'谁能拿到什么'——客户端是不可信的。"

**延伸一问："那 HR 点小眼睛看明文，不还是要传过来？"**——对，但正确做法是**独立的明文接口**：列表接口只返回打码数据；点查看时单独请求，单独鉴权、落审计日志。这次请求不是浪费，是**权限为这一次明文查看做实时背书**——HR 被降职的瞬间，本地缓存的方案他还能看，每次请求的方案他已经 403 了。而且合规要求明文访问可追溯（谁、何时、看了谁），前端本地翻转完全没有留痕。

**再延伸："能看这个字段 = 能看明文？"**——不成立。MASKED 档的打码值**本身就是被授权的数据**，"看打码版"和"看明文版"是两种权限。如果能看到字段就给明文，脱敏档就成了安全表演。

## Q3.6 行级和字段级权限的区别？（两个正交维度）

用 Excel 理解：**行级决定表里有几行，字段级决定每行有几列**。同一个用户视角下：

- 行级：技术部员工登录，产品部的行**根本不在查询结果里**（不是"出现但隐藏"）；
- 字段级：薪资列对非 HR 整列消失。

**执行位置完全不同**（这是高频考点）：

- 行级在 **SQL 层**：`EmployeeService.java L41`——非全部门角色时，`effectiveDeptId = user.getDeptId()` **强制覆盖**前端传的部门参数。用户在 URL 里写 `?deptId=1` 想看别的部门？参数直接被丢弃，SQL 查的还是他自己的部门。**行级权限防的就是"改请求参数偷看"。**
- 字段级在 **Java 转换层**：实体转 VO 时逐字段查矩阵。

为什么不能合并成一个权限：HR 和高层行范围一样（全部门）但字段不同；部门管理员和考勤员行范围一样（本部门）但字段不同——两个维度各自独立变化，拆开是必然。

## Q3.7 跨部门降级怎么实现？

代码位置：`EmployeeService.java L72`（`effectiveRole` 方法）。

考勤员查本部门张伟 → 用考勤员自己的字典（考勤号明文）；查产品部赵六 → 字典**换成普通员工的**（考勤号打码）。

**机制的本质**：降级不是写了一套"跨部门规则"，只是**换一本字典再查**。同一行代码，喂的字典不同，输出不同。这就是矩阵抽象的弹性。

## Q3.8 完整矩阵（背下来）

```
级别           │ HR  │ 高层 │ 部门管理员 │ 考勤员 │ 员工
──────────────┼─────┼──────┼───────────┼────────┼──────
PUBLIC        │ 明文│ 明文 │ 明文      │ 明文   │ 明文
INTERNAL      │ 明文│ 明文 │ 明文      │ 明文   │ 打码
SENSITIVE     │ 明文│ 打码 │ 打码      │ 打码   │ 打码
CONFIDENTIAL  │ 明文│ 隐藏 │ 打码      │ 隐藏   │ 隐藏
SALARY        │ 明文│ 隐藏 │ 隐藏      │ 隐藏   │ 隐藏
```

**为什么要 SensitiveLevel 中间层**：字段不直接挂角色而是挂级别——5 角色 × 14 字段 = 70 条规则，收敛成 5 个级别定义 + 5×5 矩阵 = 30 条，且**新增字段只需归级别，所有角色自动生效**。

## Q3.9 脱敏规则写在哪？

收敛在 `MaskUtils` 工具类：手机号 `138****5678`、身份证前 3 后 4、银行卡前 4 后 4、邮箱 `zh****@oa.com`。业务代码只调方法。反面：脱敏逻辑散在各个接口，同一个手机号两个接口打码不一致，合规审计没法统一口径。

## Q3.10 为什么不在 SQL 里只查可见的列？

可以做，但权限逻辑就要写进每个查询，规则散了。当前"SQL 查全列、转换层统一裁剪"牺牲一点查询冗余，换权限规则**一处维护**。列表页吞吐大的场景可以演进为只查可见列，矩阵不动。

# 模块四：数据库（就 3 张表）

## Q4.1 一共几张表？权限存哪？

**3 张**：department（部门）、sys_user（登录账号）、employee（花名册）。

**没有权限表**——sys_user 只存 role 字符串和 dept_id 两个值，规则全在 Java 枚举里。数据库存"事实"，代码存"规则"。

## Q4.2 每张表的关键字段和设计理由

**department**：id、name(UNIQUE)。作用：导入时"部门名 → ID"的翻译字典。

**sys_user**：id、username(UNIQUE)、password_hash（MD5，生产应换 BCrypt）、**role**（存 'HR' 这样的字符串，字段级权限的全部数据来源）、**dept_id**（行级权限依据）。

**employee** 13 个字段，关键设计：

| 字段 | 为什么这么设计 |
|---|---|
| emp_no（UNIQUE） | 唯一索引 = 幂等的数据库层兜底，并发插入相同工号被数据库直接拒绝 |
| dept_id（建索引） | 行级权限的查询永远带 `WHERE dept_id=?`，所以要索引 |
| salary NUMERIC(12,2) | 绝不用 float/double（二进制浮点有误差），钱用十进制精确 |
| 敏感字段 | **库里存明文**（HR 要用），脱敏是查询时在 Java 层做的 |

## Q4.3 完整请求流程（考勤员查花名册，10 步）

```
① 前端登录页 POST /api/auth/login {username, password}
② 后端查 sys_user 表 → 比对密码 → 生成 token 存内存 Map
   → 返回 {token, role:'ATTENDANCE', deptId:1}（角色下发给前端）
③ 前端 token/role 存 localStorage；请求拦截器从此自动带 X-Auth-Token
④ GET /api/employees?page=0
⑤ 登录拦截器：请求头取 token → 内存 Map 查出用户 → ThreadLocal
   （LoginInterceptor.java L25-L34）
⑥ Service：考勤员的范围是"本部门" ≠ "全部门"
   → 查询条件强制覆盖为本部门（前端传参被忽略）
   → SQL: WHERE dept_id = 1
⑦ toVO() 逐字段查考勤员字典：手机号→打码、身份证→不赋值、薪资→不赋值
⑧ 序列化：null 字段连 key 都不出现
⑨ 返回 {"code":200,"data":{...打码后的数据...}}
⑩ 前端响应拦截器解包 → 按角色白名单渲染列（隐藏列连表头都不创建）
```

**注意两个易错点**（二轮面试真踩过）：
- token 在**请求头**（X-Auth-Token），不在请求体；
- 角色存在 **sys_user 表**，不在 employee 表；而且拦截器查 token 时已经带出完整用户信息，不需要再查表。

# 模块五：MyBatis 与事务

## Q5.1 为什么选 MyBatis 不用 JPA？

> "SQL 全手写可控：批量插入用 foreach 拼一条多值 SQL、动态条件用 XML 里的 if/where 标签，复杂查询的执行计划心里有数。JPA 在简单 CRUD 上快，但批量、调优的场景要绕着它的抽象走。"

## Q5.2 TransactionTemplate 包住 mapper 调用，也是原子的吗？

**是。** 关键认知：**事务绑在数据库连接上，不绑在框架上**。

执行过程：TransactionTemplate 拿一条数据库连接、关掉自动提交、把连接绑定到当前线程 → MyBatis 执行 SQL 时发现线程上已有事务连接，直接复用 → 里面的 SQL 全跑在这一条连接上 → lambda 正常结束就 commit，抛异常就 rollback。JPA、MyBatis、JdbcTemplate 都只是"往连接上发 SQL 的不同工具"。

**这题里其实有两层原子性**（能说出来是加分项）：

1. foreach 拼出来的多值 INSERT 是**一条 SQL**——单条语句在数据库里天然全成全败，理论上不包事务也原子；
2. 事务是为"一批多条语句"（比如以后加"插员工+更新计数"）和未来扩展准备的。

代码位置：`ExcelImportService.java L180`。

## Q5.3 JPA saveAll 和 MyBatis foreach 批量插入的区别？

| | JPA saveAll + 配置 | MyBatis foreach |
|---|---|---|
| 数据库收到什么 | 500 条独立 INSERT（JDBC batch 打包一次往返） | **1 条**多值 INSERT |
| 原子性来源 | 事务（没有事务就 500 条各自提交） | SQL 语句本身 + 事务双保险 |
| 生效前提 | 必须配 batch_size，不配退化为逐条往返 | 零配置 |

**foreach 的边界**：一条 SQL 有长度限制，批太大报错——批次设 500 的另一个理由。量再大上 PG 的 COPY。

代码位置：`EmployeeMapper.java L41` + `EmployeeMapper.xml`（foreach）。

## Q5.4 为什么用 TransactionTemplate 不用 @Transactional 注解？

`@Transactional` 的粒度是**方法**——进方法开事务，出方法提交，整个方法一个事务。而这里需要**循环里每一轮开一个新事务**（批间隔离），注解做不到（除非把循环体拆到另一个 Bean，而且同类自调用注解还不生效）。编程式事务想在哪开就在哪开，意图更直白。

# 模块六：前端（Axios / React / TypeScript）

## Q6.1 Axios 拦截器具体做了什么？

代码位置：`request.ts L62`（请求拦截器）、`L73`（响应拦截器）。

**请求拦截器**：统一注入 X-Auth-Token——业务代码永远不写 header。

**响应拦截器**：
1. 统一解包：后端所有接口都返回 `{code, message, data}`，拦截器在 code=200 时直接返回 data 本体，业务代码拿到的就是干净数据，不用层层 `.res.data.data`；
2. 错误统一处理：业务错误弹提示，401 清 token 跳登录页——全项目只写一次；
3. Dashboard 历史接口的敏感字段剔除（`request.ts L55`，仅展示层控制）。

## Q6.2 为什么放拦截器，不放每个页面？（横切逻辑收敛）

token 注入、解包、401 处理是**所有请求共同的行为**。放页面里 = 复制粘贴 N 遍还容易漏；拦截器是 Axios 提供的"切面"机制，一处配置全局生效。和后端拦截器做登录校验、全局异常处理器兜异常是同一个思想：**横向的通用逻辑下沉，业务代码只留业务**。

## Q6.3 拦截器自己抛异常会怎样？

异常沿着 Promise 链往后传，调用方的 .catch 能接到——页面不会崩，但这次请求算失败。正确姿势：拦截器内部自己 try-catch，别让解包逻辑的 bug 污染所有请求。

## Q6.4 前端字段处理的三个时机（别混）

| 时机 | 位置 | 做法 | 场景 |
|---|---|---|---|
| 渲染层 | React 组件 | 按角色白名单过滤列定义，隐藏列的 th/td **根本不创建** | 花名册（后端已过滤，前端控 UI） |
| 响应拦截器 | Axios | delete 响应里的字段 | Dashboard（历史接口，展示层删除） |
| 请求拦截器 | Axios | delete 请求体里的字段 | 表单提交防敏感字段带出去 |

一句话：**后端管"给不给"，渲染层管"画不画"，拦截器管"数据进出浏览器时的清洗"。安全责任只在后端。**

## Q6.5 React 按角色控制列怎么写的？

代码位置：`Roster.tsx L27`（ROLE_VISIBLE 白名单）。

```ts
const visibleColumns = ALL_COLUMNS.filter(c => ROLE_VISIBLE[role].includes(c.key));
```

只渲染 visibleColumns——被过滤的列**连表头都不创建**，DOM 里不存在。注意不是"渲染空列"：留空 = 表头位置还在，用户会疑惑"这里藏着东西"。

与后端矩阵形成双保险：后端漏配多返回了字段，前端白名单也只画自己的列。

## Q6.6 角色从哪来？（二轮面试踩过的坑，记牢）

- **后端角色**：sys_user 表 → 登录拦截器查 token 带出用户 → ThreadLocal。**不是什么"外部 SDK"。**
- **前端角色**：登录接口的响应下发 → localStorage → 渲染时查白名单。被篡改最多看到空列（数据后端已过滤），不会泄露。

## Q6.7 TS 迁移踩过什么坑？（第一手素材，比八股可信）

1. **闭包丢失窄化**：`let el` 在 `if (!el)` 里判断过，但 `setTimeout` 回调里 TS 又报"可能为 null"——TS 的类型收窄不把 let 变量的判断带进回调（回调将来执行时 let 可能被重新赋值）。修法：`const el = existing ?? createElement(...)` 一次性收敛成永不为 null 的 const。
2. **CSS 导入报错**：`import './styles.css'` 报 TS2882——需要 `vite-env.d.ts` 声明文件为非代码资源提供类型（`/// <reference types="vite/client" />`）。
3. **拦截器类型失真**：拦截器"偷换"了响应体，Axios 的类型签名就不再准确——用一层 `request.get<T>(): Promise<T>` 包装修正契约。
4. **权限语义编进类型**：敏感字段用可选属性 `phone?: string`，类型层面就表达了"没权限时后端不返回这个 key"。

## Q6.8 跨域怎么处理的？

开发期：Vite 的 proxy 把 `/api` 请求转发到后端 8080——浏览器以为是同源，不发预检。生产期：Nginx 做同样的反向代理。

## Q6.9 异步导入的前端怎么写的？

代码位置：`Roster.tsx L63`（轮询）、`L81`（上传）。

上传后拿到 taskId → 每秒轮询一次任务状态（PENDING/RUNNING/SUCCESS/FAILED）→ 进行中显示"已处理 N 行"→ 终态停止轮询 → 成功且有失败行时展开行级错误报告 → 刷新列表。

轮询用 `setTimeout` 递归而不是 `setInterval`：每次轮询完成后再定下一次，避免请求堆积。

## Q6.10 token 存 localStorage 有什么问题？

有 XSS 风险（页面里的恶意脚本能读它）。严格场景用 HttpOnly Cookie（JS 读不到）。当前项目是已知简化。

# 模块七：Java 基础（面试官顺手就问）

## Q7.1 ThreadLocal 是干嘛的？为什么必须 remove？

- **作用**：在同一个请求内共享登录用户，任何一层代码都能直接取，不用层层传参。
- **remove 的第一理由（先说这个）**：Tomcat 线程池**复用线程**，不清理的话下一个请求可能读到上一个用户的身份——**串号是最严重的权限事故**。
- **第二理由**：内存泄漏——ThreadLocalMap 的 key 是弱引用、value 是强引用，不 remove 的 value 滞留。

代码位置：`LoginInterceptor.java L34`（set）、`L40`（clear，在 afterCompletion 里）。

## Q7.2 @Transactional 什么原理？什么时候失效？

原理：AOP 动态代理，方法前后开/提交事务。

失效场景（高频）：**同类自调用**（代理不生效，最常考）、方法不是 public、异常被 catch 吞掉、默认只回滚 RuntimeException。

传播行为：REQUIRED（默认，加入当前事务）/ REQUIRES_NEW（挂起外层、开新事务——"批间隔离"的另一种实现路径）。

## Q7.3 N+1 问题？

列表页每行员工都触发一次部门查询 = 1+N 次 SQL。解法：部门表小，一次全捞建内存 Map（`deptIdByName.get(...)` 秒出）。

## Q7.4 线程池的核心参数？（配合 Q2.14）

七个参数背全：核心线程数、最大线程数、空闲回收时间、工作队列、线程工厂、拒绝策略。执行顺序：核心线程 → 队列 → 扩容到最大线程 → 拒绝策略（**注意：队列满了才扩容，不是线程满了进队列**——这是最常考的细节）。

# 模块八：复盘题（主动交短板）

> "核心业务链路——导入管线和权限脱敏——是按生产标准做的；简化的是鉴权基建，因为是内部项目。但每一处简化我都知道对应的正确方案。"

**优先改进三点**：

1. **鉴权基建**：token 存内存 Map（重启失效、多实例不共享）、密码 MD5。生产：Redis 存 token（带过期、多实例共享、能踢人下线）+ BCrypt（自带盐、慢哈希抗撞库），或直接上 Spring Security。
2. **导入并发幂等强保证**：异步化后并发上传真的可能撞工号，当前没 catch 唯一约束冲突。补法：catch `DataIntegrityViolationException` 降级逐行插入，冲突行计入错误报告。
3. **敏感数据访问审计**：HR 查看明文应落审计日志（谁、何时、看了谁、IP）——合规硬要求。

其他已知简化（被问到再交）：任务状态内存存储（生产落库/Redis）；前端 token 放 localStorage（XSS 风险）；toVO 手写 if 繁琐（演进为注解+序列化器）。
